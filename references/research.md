# Researching reference listings

Do this **before** designing anything. The goal is not imitation — it is knowing
the conventions of the category so the set reads as a credible competitor rather
than a generic template.

## Where to look

Search the storefront the tiles are destined for, in the app's actual category.

- **Google Play** — `https://play.google.com/store/search?q=<category>&c=apps`
- **App Store** — `https://apps.apple.com/us/search?term=<category>`
- Also check the app's *own* marketing site — it defines the brand voice the
  tiles must match.

Open the top 3–5 listings. Prefer ones with high install counts and recent
updates; a polished listing on a dead app is not evidence of what converts.

## What to record

For each reference listing:

| Dimension | What to note |
|---|---|
| Headline length | Word count, and whether it survives at thumbnail size |
| Copy position | Above the device, below it, or beside it |
| Continuity | Is there a motif — band, line, gradient — running across all tiles? |
| First tile | How does it differ from the rest? Usually it carries the core promise |
| Device treatment | Straight, tilted, cropped by the frame, multiple devices |
| Proof elements | Ratings, user counts, awards, "as seen in" |
| Colour | How many colours, and how saturated relative to the store's white chrome |
| Density | Full app screens, or zoomed detail crops? |

## How to judge what you find

- **Continuity is what separates a designed set from six posters.** The best sets
  run a single visual element edge to edge across every tile so the strip reads as
  one thing when scrolled.
- **Thumbnail legibility beats detail.** Most impressions happen at grid size. If
  a headline needs more than a glance, it fails regardless of how it looks at 100%.
- **Category norms are real.** Utility and productivity listings lean clean and
  typographic; games and consumer social lean dense and saturated. Match the
  category's register, then be the most polished entry in it.
- **Copy in reference listings is often weak** — plain feature labels like "Units",
  "Maps", "Settings". Matching their layout quality while beating their copy is
  usually the highest-value move available.

## Reporting back

Summarise for the user before building: what the category does, which specific
conventions you are adopting, and where you intend to deviate and why. This is
also the moment to agree the copy table (tile → headline → support card) so
rendering is not wasted on unapproved wording.

## Category conventions are not transferable

Research the store the tiles are destined for, not "app listings" in general.
The conventions differ sharply and copying the wrong one costs rounds:

- **Mac App Store, utilities.** CleanMyMac: short headline above a large app
  window on a vivid field. DaisyDisk (Editors' Choice): the raw app window on a
  desktop wallpaper, no marketing copy at all. Nobody uses a floating 3D app
  icon. Tiles render wide, so the UI *is* the sell.
- **Play Store / iOS consumer.** The floating-3D-icon hero with orbiting props
  is a mobile convention. It looks premium in a phone-sized grid and out of
  place on a Mac listing.

If a reference the user loves comes from a different store, say so before
building. A composition can be beautiful and still be wrong for the storefront.

## Let the rejection drive the set

When a listing was rejected under **Guideline 2.3** ("we were unable to locate
some of the features described in your metadata"), every tile that shows no app
UI is a wasted slot. Make each tile prove a named feature exists and where it
lives. That is a stronger argument to the reviewer than any hero object.
